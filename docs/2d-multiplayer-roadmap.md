# Futty 2D · 3D · Multiplayer 확장 개발 계획

> 기준: 2026-11-21, hwanghj09/futty main. 이 문서는 **개발 계획**이며 구현 완료 보고서가 아니다.  
> 원칙: **AI가 MCP/CLI만으로 게임을 생성·수정·검증·빌드할 수 있어야 한다.** 사람용 에디터는 선택적 보조 도구로 유지한다.

관련 문서: [AI-first 로드맵](ai-roadmap.md) · [현재 개발 체크리스트](development-checklist.md) · [MCP 가이드](guide.md)

## 0. 최종 목표와 지원 범위

Futty는 하나의 프로젝트 시스템과 런타임 위에서 다음 네 가지 게임 유형을 만들 수 있어야 한다.

| 게임 유형 | 게임 예 | 필수 제공 기능 |
| --- | --- | --- |
| 2D 싱글플레이 | 플랫폼, 퍼즐, 탑다운 RPG | Sprite2D, 2D 물리, 타일맵, 2D 카메라 |
| 3D 싱글플레이 | FPS, 어드벤처 | 기존 3D 렌더링/물리/에셋 보존 |
| 2D 멀티플레이 | 2~4인 협동, 대전 | 접속, 방, 입력, 서버 판정, 상태 동기화 |
| 3D 멀티플레이 | 협동 액션, FPS | 동일한 네트워크 서비스의 3D 적용 |

**초기 타깃**: Windows x64 네이티브 클라이언트와 전용 서버. 브라우저, 모바일, 콘솔 및 수백 명 규모 MMO는 후속 범위다. 별도 로그인/매치메이킹 서비스도 첫 MVP 필수 조건으로 두지 않는다.

### 완료 판정의 최상위 기준

1. AI가 새 빈 폴더에서 2D 혹은 3D 프로젝트를 생성한다.
2. AI가 에셋·조작·스크립트·물리·HUD·네트워크 규칙을 직접 설정한다.
3. AI가 **실제 두 개 이상의 클라이언트와 서버**를 자동 실행해 플레이 결과를 검증한다.
4. 실패 시 구조화된 오류를 받고 재현·수정·재시험한다.
5. 사용자 GUI 조작 0회로 **Game.exe + 전용 Server 실행 파일**을 빌드한다.
6. 기존 3D 예제와 구버전 씬의 로드·실행·내보내기 회귀 테스트가 통과한다.

## 1. 현재 코드 기준점

실제로 존재하는 구성:
- **futty-core**: 공통 Transform(Vec3, Quat), 에셋/카메라/렌더 자료형
- **futty-runtime**: bevy_ecs, Rhai, 씬/프로젝트/오브젝트, 입력, HUD, 물리, Sprite3D
- **물리**: rapier3d 기반; 2D 전용 충돌/강체 시스템은 아직 없음
- **렌더링**: wgpu 30과 WGSL 기반 3D 렌더러; Sprite3D는 3D 공간의 이미지 평면
- **futty-mcp**: 씬/프로젝트 편집, 에셋/스크립트/HUD, 플레이테스트, 캡처, 패키징 등 등록된 도구
- **futty-build**: 준비된 Windows 실행 파일을 복사해 게임과 필요한 에셋을 패키징
- **CI**: Windows 포맷/Clippy/전체 테스트/릴리스 빌드

**주의**: Sprite3D와 정사영 카메라가 있다고 해서 TileMap·SpriteAnimation·Rapier2D를 갖춘 2D 엔진인 것은 아니다. 네트워크 동기화·전용 서버는 새로 구현해야 한다. 개발 체크리스트의 기존 3D AI E2E 코인 수집 게임도 아직 완전 통과 기준이 남아 있다.

## 2. 설계 결정: 공통 런타임, 분리된 표현/물리

~~~text
AI Agent (Codex / Claude / 기타)
           |
      Futty MCP / CLI
           |
   공통 제작 서비스(씬/에셋/테스트/빌드)
           |
       futty-core
           |
      futty-runtime (ECS · 스크립트 · 입력 · 고정 틱)
       /        |         \
  Render2D   Render3D    futty-network
  Rapier2D   Rapier3D    authoritative server
       \        |         /
       프로젝트/씬 포맷 + 공통 게임 빌더
~~~

- 2D와 3D는 **같은 ECS, 프로젝트 메타데이터, 에셋 레지스트리, 스크립트 시스템**을 공유한다.
- 씬 단위로 **SceneDimension = TwoD | ThreeD**를 지정한다. 기존 씬의 누락 값은 무조건 ThreeD로 해석한다.
- 2D 좌표는 **XY 평면, Y 위쪽, Z=0**, 2D 회전은 스칼라 각도로 표시한다. 내부 Transform3D를 재사용하더라도 2D 전용 래퍼와 제약 검증을 둔다.
- 2D 물리와 3D 물리는 서로 다른 백엔드로 분기한다. 한 씬에서 혼합 물리 시뮬레이션은 초기 범위에서 제외한다.
- 하나의 프로젝트에 2D·3D 씬을 함께 등록할 수 있도록 포맷을 설계하되, **서로 다른 차원 씬의 전환 검증은 별도 마일스톤**으로 둔다.
- 렌더링과 네트워크를 분리한다. 전용 서버는 GPU와 창이 없어도 실행되어야 한다.
- 모든 추가 기능은 에디터 버튼보다 **MCP/CLI/재사용 Rust API** 구현을 우선한다.

### 제안 크레이트 구조

| 경로 | 책임 | 변경 방식 |
| --- | --- | --- |
| crates/futty-core | SceneDimension, 좌표/직렬화 공통 타입 | 확장 |
| crates/futty-runtime | ECS, 게임 상태, 고정 틱, 2D/3D 공통 동작 | 확장 |
| crates/futty-render | 렌더 공통 인터페이스 및 기존 3D | 확장 |
| crates/futty-render-2d | 2D 스프라이트/타일맵 파이프라인 | 신규 제안 |
| crates/futty-physics-2d | Rapier2D 어댑터, 2D 충돌 이벤트 | 신규 제안 |
| crates/futty-network | 프로토콜, 접속, 룸, 복제, 예측/보간 | 신규 제안 |
| crates/futty-server | GUI 없는 권한 서버 실행 진입점 | 신규 제안 |
| crates/futty-mcp | 2D/네트워크 설정 및 검증 도구 | 확장 |
| crates/futty-build | 2D/3D 클라이언트 + 서버 패키징 | 확장 |
| crates/futty-editor | 2D 뷰/인스펙터/멀티플레이 디버그 UI | 후순위 확장 |

위 경로는 설계안이며 실제 소스에 아직 모두 존재하지 않는다. 처음에는 기존 크레이트의 모듈로 실험하고 독립성이 확인되면 크레이트로 분리해도 된다.

## 3. 단계별 개발 계획

### Phase 0 — 기존 3D 기준선 확보 (필수 선행)

- [ ] 기존 3D AI E2E 코인 수집 게임을 빈 폴더에서 제작하고 GUI 없이 검사·빌드한다.
- [ ] Pulse Range / Beacon Bot Escape의 씬 로드, 스크립트, 물리, 캡처, Windows 내보내기 회귀 테스트 고정.
- [ ] 씬 직렬화 마이그레이션 테스트와 에셋 참조/UUID 보존 테스트 구축.
- [ ] 런타임의 고정 틱과 렌더링 프레임을 구분하고 Headless 테스트 경로를 문서화.

**완료 기준**: 이전 3D 기능을 유지한 채 자동 제작 및 Windows 빌드가 CI에서 재현된다.

### Phase 1 — 차원(2D/3D) 모델과 포맷

- [ ] SceneDimension enum 추가 (기본값 ThreeD).
- [ ] 2D Transform 래퍼(Position Vec2, Angle, Scale Vec2), 좌표/깊이 규칙 정의.
- [ ] Renderable2D/Collider2D/Body2D를 기존 3D 컴포넌트와 구분.
- [ ] 이전 RON 씬과 프로젝트를 읽고 다시 저장하는 마이그레이션 테스트.
- [ ] MCP의 scene_create/scene_inspect/scene_validate/scene_apply에 차원 정보 연결.
- [ ] 구버전 씬에 없는 필드를 ThreeD로 기본 해석하고 2D 씬 오류는 필드 경로와 함께 반환.

**완료 기준**: 구버전 3D 씬은 동일하게 열리고, TwoD 씬 생성·저장·재조회가 GUI 없이 통과한다.

### Phase 2 — 실사용 가능한 2D 렌더링

- [ ] wgpu Sprite2D 파이프라인 구축: 텍스처, 알파 블렌딩, 카메라, 정렬 순서, 배치 렌더.
- [ ] 2D 카메라: 화면 크기, Orthographic, 픽셀 스냅/픽셀 퍼펙트 옵션, 추적/줌.
- [ ] SpriteSheet/Atlas + AnimationClip: 프레임/속도/반복/상태 전환.
- [ ] TileSet/TileMap: 레이어, 그리드 좌표, 청크/뷰 컬링, 타일별 충돌 태그.
- [ ] 기존 PNG 및 에셋 UUID/재가져오기 로직 재사용.
- [ ] Scene 캡처가 2D 카메라 PNG를 생성하도록 확대.
- [ ] 렌더링/타일맵/애니메이션의 오프스크린 이미지 회귀 테스트 구축.

**완료 기준**: 2D 씬을 저장·재로딩해도 카메라·레이어·애니메이션 결과가 유지되며 캡처 가능.

### Phase 3 — 2D 게임플레이와 물리

- [ ] Rapier2D 기반 RigidBody2D, Collider2D (박스·원·캡슐), 센서/트리거/레이캐스트.
- [ ] 2D 전용 이동 컨트롤러(횡스크롤/탑다운), 중력/점프/마찰/충돌 레이어.
- [ ] Rhai 게임 API에 2D 위치·속도·충돌/트리거 이벤트를 안전하게 추가.
- [ ] 2D 입력 프로필과 HUD/오디오/씬 전환 재사용.
- [ ] Fixed-step 시뮬레이션과 플레이테스트 입력 기록.
- [ ] 첫 예제: **2D Coin Runner** (이동→점프→코인 획득→점수 HUD→승리).

**완료 기준**: AI가 생성한 2D Coin Runner가 충돌·점수·종료 조건 테스트를 통과하고 Game.exe로 패키징된다.

### Phase 4 — AI를 위한 2D 제작 API

- [ ] 기존 scene_apply 일괄 편집에 sprite2d/tilemap/physics2d/animation 생성·수정 작업 추가.
- [ ] 고수준 API: 2D 프로젝트 생성, 2D 프리팹 배치, 타일맵 일괄 쓰기, 애니메이션 설정.
- [ ] 입력값/좌표/단위/UUID/허용 범위를 JSON 스키마로 기술하고 오류를 기계가 읽는 형태로 반환.
- [ ] 새 2D 프로젝트에 대한 헤드리스 테스트·카메라 캡처·Windows 내보내기 연결.
- [ ] 에셋 원본이 없는 경우도 진단 가능하도록 프로젝트 검사 확대.

**완료 기준**: GUI를 열지 않고 MCP 호출만으로 2D 싱글플레이를 처음부터 끝까지 제작한다.

### Phase 5 — 멀티플레이 네트워크 기초

- [ ] 렌더러에 의존하지 않는 futty-network/futty-server 설계.
- [ ] **서버 권한(authoritative server)** 모델: 클라이언트는 입력 전송, 서버가 공식 게임 상태 계산.
- [ ] 세션/방: 로컬 호스트, LAN, 직접 주소 온라인 접속, 입장/퇴장/재접속 정책.
- [ ] 프로토콜 버전, 연결 핸드셰이크, 세션 토큰, 최대 플레이어 수, 타임아웃/Heartbeat.
- [ ] 고정 틱 서버 루프, 연결별 입력 시퀀스 번호, 서버 Tick, 상태 스냅샷 전송.
- [ ] 전송 계층 추상화 도입. 네이티브 MVP는 QUIC(예: quinn) 후보; 신뢰성 전송과 비신뢰성 Datagram을 메시지 종류에 따라 선택한다. 웹 지원 시 WebSocket/WebTransport 등 별도 검토.
- [ ] 서버는 입력/요청을 신뢰하지 않고 크기·빈도·값 범위·권한을 검증한다.

**완료 기준**: 2개의 Windows 클라이언트가 단일 Headless 서버에 접속하고 동일한 오브젝트 상태를 관찰한다.

### Phase 6 — 복제, 예측, 네트워크 게임 로직

- [ ] NetworkIdentity 및 스폰·디스폰 소유권(Owner/Server)을 명확히 정의.
- [ ] 컴포넌트/필드별 Replication 설정: 전체, 관심 영역, 비공개 서버 상태를 구분.
- [ ] 중요 이벤트(생성/파괴/점수/씬 이동)는 신뢰성 전송; 높은 빈도의 위치는 스냅샷/델타 전송.
- [ ] 원격 플레이어 렌더는 보간(Interpolation), 로컬 조작은 예측(Prediction) 및 서버 재조정(Reconciliation) 도입.
- [ ] 충돌/피해/보상/승리 판정과 중요한 랜덤 추첨은 서버에서 수행.
- [ ] 접속 해제/재접속/중복 이벤트/역순 패킷/지연/손실 대응 테스트.
- [ ] 전용 서버의 로깅, 종료 처리, 네트워크 상태 통계 추가.

**초기 목표값(설계 가정, 실측 후 조정)**:
- 서버 물리/게임 시뮬레이션: 60Hz
- 상태 스냅샷: 10~20Hz부터 시작
- 첫 멀티플레이 예제: 2~4인
- 고정 틱이 있다고 해서 Rapier 물리의 플랫폼 간 비트 단위 결정성이 자동 보장되는 것은 아니다. 서버를 유일한 공식 상태로 둔다.

**완료 기준**: 100ms 왕복 지연, 지터/패킷 손실을 주입해도 플레이어 위치 및 점수 상태가 최종적으로 수렴하고 중복 보상이 발생하지 않는다.

### Phase 7 — 2D 멀티플레이 완제품 테스트

- [ ] 예제: **2D Co-op Coin Hunt** (최대 4인, 방 입장, 이동, 공동 코인 수집, 공통 점수, 승리).
- [ ] AI가 서버 구성, 플레이어 스폰, Replication 규칙, 룸 제한을 자동 작성.
- [ ] Headless 테스트가 서버 1개와 클라이언트 2개 이상을 독립 프로세스로 실행.
- [ ] 동기화 검사: 동일 코인 중복 획득 방지, 플레이어 접속/퇴장, 점수 공유, 승리 일치.
- [ ] Game.exe 및 Server.exe와 필수 에셋 패키징; 실제 별도 Windows 머신에서 수동 스모크 테스트.

**완료 기준**: AI가 빈 프로젝트에서 완성한 2D 온라인 협동 게임을 두 클라이언트가 함께 플레이하며 자동 테스트가 통과한다.

### Phase 8 — 3D 멀티플레이 확장

- [ ] 기존 3D Runtime/Physics에 동일한 NetworkIdentity/Replication/입력 프로토콜 적용.
- [ ] 3D 이동·회전, 애니메이션·상태, 물리 이벤트, 상호작용 동기화.
- [ ] 3D 협동 예제 우선 제작; 이후 FPS의 서버 권한 명중/피해 판정 구현.
- [ ] 부정 입력(순간이동, 과속, 발사 쿨다운 무시, 존재하지 않는 객체 조작) 거절 테스트.
- [ ] 2D/3D가 동일 서버/프로토콜 모듈을 사용하도록 중복 제거.

**완료 기준**: 3D 협동 게임에 두 사람이 접속해 위치·상호작용·결과가 일치하며 Windows 클라이언트/서버 빌드가 성공한다.

### Phase 9 — AI 자동 제작 파이프라인

- [ ] 제작 템플릿: 2D 플랫폼/탑다운/협동, 3D 협동/FPS의 최소 생성물.
- [ ] AI가 프로젝트 요구 사항을 검사하고 2D/3D/멀티플레이 설정을 도구 호출로 구성.
- [ ] validate → build → server_launch → clients_launch → network_test → capture → report를 자동 연결.
- [ ] 실패 리포트에 프로젝트·씬 ID, 오브젝트 ID, 서버/클라이언트 로그, 틱, 입력 리플레이, 스크린샷 포함.
- [ ] 실패 후 수정 및 재검증을 새 폴더에서 반복 실행하는 E2E CI 마련.

**완료 기준**: AI가 사용자 한 번의 지시로 2D/3D 온라인 게임 하나를 제작·테스트·패키징하고 결과를 보고한다.

## 4. 신규 MCP API 제안

아래는 **계약 설계안**이다. 현재 구현됐다고 가정하지 말 것. 기존 도구로 표현 가능한 경우 별도 저수준 API를 중복 구현하지 않고 scene_apply 등의 스키마를 확장한다.

| 기능 | 제안 API | 기대 출력/검증 |
| --- | --- | --- |
| 씬 차원 | scene_set_dimension | dimension, 변경된 씬 ID |
| 2D 구성 | sprite2d_create, tilemap_apply | 생성/변경 ID, 배치 수, 검증 결과 |
| 2D 물리 | physics2d_set_body | 충돌체 종류, 단위/허용 범위 |
| 2D 애니메이션 | sprite_animation_set | atlas ID, 프레임, 반복 정보 |
| 네트워크 구성 | network_configure | server mode, tick rate, max players |
| 권한/복제 | network_set_authority, network_set_replication | 권한과 동기화 대상 필드 |
| 플레이어 | network_set_player_spawn | 스폰 위치와 엔티티 프리팹 |
| 검증 | network_validate, multiplayer_test | 결과, tick, 접속 수, 불일치 |
| 패키징 | project_build_client, project_build_server | 산출물 경로, 서버 실행 옵션 |

### 요청·응답 계약 원칙

1. 모든 요청은 워크스페이스 상대 경로를 사용하고 디렉터리 이탈을 금지한다.
2. 각 API는 API/씬/프로토콜 버전과 필수 파라미터를 문서화한다.
3. 변형 작업은 적용 전 유효성 검사와 실패 시 원자적 롤백을 지원한다.
4. 상태를 조회할 수 없는 편집 옵션은 추가하지 않는다(읽기·쓰기 대칭성).
5. ID/UUID, 오류 코드, 필드 경로, 서버 틱, 결과 파일 경로를 구조화해 반환한다.
6. 재시도 시 객체가 중복 생성되지 않도록 request ID 또는 idempotency 정책을 제공한다.
7. 게임 테스트는 GUI 없이 실행할 수 있어야 하며, GPU가 필요한 캡처는 별도 경로로 분리한다.

## 5. 호환성 및 기술적 위험

| 위험 | 대응 |
| --- | --- |
| 기존 Scene 포맷 파손 | format_version 증가, serde 기본값, 이전 씬 픽스처 회귀 테스트 |
| 2D 좌표와 3D Transform 혼용 | XY/Y-up/Z=0 기준 명시, 각도 변환 래퍼, 차원별 검증 |
| Rapier2D/3D 이벤트 차이 | 공통 이벤트 추상화 + 백엔드별 어댑터 |
| 2D 렌더 순서/알파 문제 | 레이어 + order + 안정 정렬, 픽셀/캡처 테스트 |
| 네트워크와 ECS 결합 과도 | NetState/Replication 계층을 독립 크레이트로 유지 |
| 클라이언트 조작/치트 | 서버 권한 판정, 입력 범위·빈도 제한, 메시지 인증 |
| 패킷 유실/역순 | 입력 시퀀스, 서버 tick, 스냅샷, 재전송 정책 |
| 플레이테스트 결정성 오해 | 서버 공식 상태 + 리플레이/상태 비교; 비트 단위 동일성 가정 금지 |
| AI의 API 오용 | 엄격한 JSON 스키마, 오류 ID, 역호환 테스트, 도구별 예제 |
| 대량 네트워크 부하 | 관심 영역(interest management), 델타 압축은 부하 측정 후 도입 |

**초기 비목표**: 완전한 NAT 자동 통과, 자체 클라우드 매치메이킹, 범용 웹 클라이언트, MMO, 분산 서버 샤딩, 서로 다른 물리 차원의 실시간 상호작용.

## 6. 검증 시나리오 / 테스트 매트릭스

| 테스트 ID | 입력 | 통과 조건 |
| --- | --- | --- |
| COMP-01 | 기존 3D 씬(차원 정보 없음) 로드 | 3D로 로드, 기존 동작 유지 |
| COMP-02 | 이전 씬 저장·재로드 | UUID·에셋 참조·카메라 손상 없음 |
| 2D-01 | AI가 Sprite2D/2D 카메라/타일맵 생성 | 저장/조회/PNG 캡처 통과 |
| 2D-02 | 점프/충돌/코인 수집 입력 | 정해진 위치/점수/승리 판정 |
| 2D-03 | 2D 프로젝트 Windows 빌드 | Game.exe 및 참조 에셋 포함 |
| NET-01 | 서버 1 + 클라이언트 2 접속 | 세션/플레이어 ID 유일 |
| NET-02 | 한 플레이어 이동 | 다른 클라이언트에 상태 전파 |
| NET-03 | 동시 코인 획득 | 서버 공식 점수 한 번만 증가 |
| NET-04 | 인위적 지연/손실/순서 변경 | 비정상 종료·중복 보상 없음 |
| NET-05 | 잘못된 입력/권한 없는 조작 | 서버에서 거절 및 기록 |
| NET-06 | 접속 해제와 재접속 | 게임별 정책에 따라 정리/재진입 |
| 3D-01 | 두 클라이언트 3D 이동/상호작용 | 위치·이벤트·결과 동기화 |
| AI-01 | 빈 폴더에서 2D/3D 멀티 생성 | GUI 0회로 E2E·클라/서버 빌드 완료 |

CI에서는 가능한 한 **로컬 loopback 기반 다중 프로세스** 검증을 수행한다. Windows 환경에서 실제 두 PC를 사용한 수동 스모크 테스트는 별도 기록한다. 렌더 스냅샷은 GPU/드라이버 차이를 고려해 허용 오차를 명시한다.

## 7. 작업 우선순위 및 의존 관계

~~~text
[0] 기존 3D E2E/회귀 기준선
  └─ [1] 씬 2D/3D 차원 모델
       ├─ [2] 2D 렌더/타일맵/애니메이션
       └─ [3] Rapier2D/2D 게임플레이
             └─ [4] 2D MCP/E2E 제작

                         └─ [6] 서버 권한 복제·예측

                                     └─ [8] 3D 멀티 확장

~~~

네트워크의 공통 프로토콜 설계는 Phase 2~4와 병렬로 진행할 수 있지만, 먼저 단일 플레이어 게임 상태·씬·입력의 계약을 안정화해야 재작업을 줄일 수 있다.

## 8. 최종 데모 제안

**사용자 요청**: “2D 픽셀아트 4인 온라인 협동 코인 수집 게임을 Futty로 만들어줘. 두 명이 동시에 같은 코인을 먹어도 점수가 중복되지 않게 하고 Windows 클라이언트와 서버를 빌드해줘.”

**AI 작업 결과물**:
- 새 2D Futty 프로젝트와 필요한 에셋/타일맵/스크립트
- 플레이어 이동, 수집, 공유 점수 HUD, 승리 조건
- 권한 서버와 복제 규칙, 테스트용 접속 설정
- Headless 자동 테스트와 동기화/네트워크 실패 리포트
- Windows Game.exe, Server.exe 및 실행 안내

이 결과가 독립된 작업 폴더에서 반복 재현되면 “2D + 멀티플레이 AI-first 제작 지원” 마일스톤을 완료한 것으로 판정한다.
