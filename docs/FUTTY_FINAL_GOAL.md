# FUTTY — 최종 제품 목표 및 통합 개발 명세

> **이 문서가 Futty의 유일한 제품 비전·기술 목표·개발 우선순위에 대한 기준 문서(Single Source of Truth)다.**  
> 기준: 2026-11-21 · 저장소: [hwanghj09/futty](https://github.com/hwanghj09/futty) · 대상 브랜치: main  
> 기존 AI-first / 개발 체크리스트 / 2D·멀티플레이 / 원스톱 에셋 제작 로드맵을 통합한다.  
> **이 문서는 목표를 정의한다. 소스에 없는 계획 기능을 이미 구현된 것처럼 설명하지 않는다.**

## 0. 한 문장으로 설명하는 Futty

**Futty는 사람이 게임 엔진 에디터를 직접 조작하지 않아도, AI 에이전트가 MCP/CLI/API를 이용해 2D·3D 싱글플레이 및 멀티플레이 게임의 기획, 디자인, 모델링, 애니메이션, 사운드, 프로그래밍, 검증, 수정, 배포까지 끝낼 수 있게 하는 Rust 기반 AI-first 게임 제작 엔진이자 도구 모음이다.**

- **1차 사용자**: Codex·Claude Code 등 Futty MCP/CLI/API를 호출하는 AI 개발 에이전트.
- **2차 사용자**: 게임을 요청하고 결과를 평가·수정 지시하는 사람.
- **에디터의 역할**: 사람의 미리보기·디버깅·선택적 편집 수단. **필수 조작 경로가 아님.**
- **Futty의 책임**: 실행 가능한 엔진, 안정적인 제작 인터페이스, 에셋 규격화, 검증, 재현, 패키징.
- **AI의 책임**: 요구 분석, 제작 계획, 콘텐츠 생성 도구 선택·호출, 구현, 실패 원인 해석과 수정.
- **의도적인 비핵심 목표**: 게임 속 AI NPC·AI 관전·AI끼리 대전 자체를 주제품으로 만들지 않는다.

### 절대 바꾸지 않을 제품 원칙

1. **Human GUI 의존 0**: 주요 제작 기능은 GUI 없이 MCP/CLI에서 제공한다.
2. **One-shot 지향, 검증은 단계별**: 사용자 한 번의 요구로 작업을 시작하지만 중간 검증·재시도와 최종 결과 보고를 생략하지 않는다.
3. **2D와 3D 공통 기반**: 프로젝트·씬·ECS·스크립트·에셋/빌드 API는 공유하고 렌더러/물리만 분리한다.
4. **멀티플레이 재사용**: 네트워크 프로토콜/권한 시스템은 2D·3D 모두에 사용하며 렌더링과 분리한다.
5. **모델 중립**: Futty는 특정 LLM, 이미지·3D·음악 생성 제공자에 종속되지 않는다.
6. **정직한 상태 표기**: 구현됨 / 소스 존재하나 통합 미검증 / 설계·계획을 항상 구별한다.
7. **실제 게임을 산출**: 예쁜 에셋이나 씬만 생성하는 것으로 성공 판정하지 않는다. 플레이 가능한 게임/서버·테스트 결과가 필요하다.
8. **안전한 자동화**: 사용자 워크스페이스와 비밀키, 비용/라이선스·서버 입력 권한을 보호한다.

### 개발 이전: 창작자의 상상 확인

자연어로 게임 제작 의뢰가 들어왔을 때 AI는 무작정 장르의 평균적인 게임을 생성하지 않는다. **사용자가 상상한 첫 장면, 재미, 감정, 모드, 규칙, 아트 방향**부터 이해한다. 특히 기획·아이디어 구상이나 미정 사항이 많은 제작 요청에는 [futty-idea-interview](../.agents/skills/futty-idea-interview/SKILL.md)를 적용해 선택형 질문과 여러 차례의 심화 인터뷰로 사용자 비전을 구체화한다. 이미 충분히 구체적인 즉시 제작 요청에는 인터뷰를 강제하지 않는다.

인터뷰 산출물인 **Game Brief**는 사용자의 확정 답변과 AI가 제안한 가정, MVP 범위, 싫어하는 요소를 구분해 기록한 후 게임 기획 및 원스톱 에셋 제작 단계로 전달한다. 질문 수가 아니라 **사용자의 상상에 얼마나 가까워졌는지**가 성공 기준이다.

## 1. 최종 지원 범위

| 유형 | 플레이 가능 게임 예 | 공통 엔진 목표 | 제작 완료 시 제출물 |
| --- | --- | --- | --- |
| 2D 싱글 | 플랫폼, 퍼즐, 탑다운 RPG | Sprite2D/TileMap/2D 물리/2D 애니메이션 | 프로젝트 + Windows Game.exe |
| 3D 싱글 | FPS, 공포, 탐험·퍼즐 | wgpu 3D/GLB/물리/Rhai | 프로젝트 + Windows Game.exe |
| 2D 멀티 | 협동 코인 수집, 2~4인 대전 | 2D + 공통 서버/복제/동기화 | 게임 클라이언트 + 전용 서버 |
| 3D 멀티 | 협동 생존, 온라인 FPS | 3D + 같은 네트워크 계층 | 게임 클라이언트 + 전용 서버 |

**최초 플랫폼**: Windows x64 게임/서버. **향후** Linux 서버와 다른 클라이언트 플랫폼을 검토. 브라우저·모바일·콘솔·MMO·클라우드 계정 시스템·자체 글로벌 매치메이킹은 첫 완성 기준에 포함하지 않는다.

### 최종 사용자 경험

사용자는 다음처럼 한 번 요청한다.

> “최대 4명이 함께 플레이하는 3D 공포 탈출 게임을 만들어줘. 폐병원을 모델링하고 괴물 캐릭터와 걷기·추적·공격 애니메이션을 제작해 줘. 발소리·환경음·BGM·로비·HUD·승리 조건을 포함하고 서버와 Windows 게임을 만들어줘.”

목표 결과:
- 요청을 해석한 **게임 기획/상호작용·승패 규칙 문서**.
- 통일된 디자인 시스템과 **이미지/3D/애니메이션/효과음/BGM/UI 에셋**.
- 에셋을 실제 장면/게임 이벤트에 연결한 **Futty 프로젝트, 씬, Rhai 스크립트, 프리팹**.
- 멀티게임일 때 **서버 권한 기반 네트워크 설정과 최소 두 클라이언트 테스트**.
- 검증·리플레이·시각/오디오·네트워크 보고서, **실행 파일 및 출처·라이선스 정보**.
- 실패한 부분을 자동 수정해 재시도하거나, 해결하지 못한 문제를 **명시적으로 보고**.

기존 로드맵에 있던 “MCP 도구 5개” 또는 “에셋·스크립트 API 미구현”과 같은 초창기 서술은 **현재 코드 상태와 맞지 않으므로 폐기**한다. API가 구현되었는지 확인할 때는 언제나 실제 MCP 도구 목록과 테스트를 우선한다.

### 이미 있는 핵심 MCP 예

- **씬/프로젝트**: scene_create, scene_inspect, scene_objects, scene_apply, scene_undo, scene_validate, project_create, project_inspect, project_set_start_scene, project_validate.
- **게임 제작**: asset_import, asset_reimport, material_create, script_create, script_update, script_attach, input_set, hud_create, hud_bind, prefab_create, prefab_instantiate, scene_transition_set.
- **검증/산출**: play_test, play_replay, scene_capture, project_build.
- 실제 도구의 정확한 이름·입력 JSON은 소스와 [MCP 가이드](guide.md)에서 확인한다. 아래의 신규 제안 API와 혼동하지 말 것.

## 3. 권장 전체 시스템 아키텍처

~~~text
사용자 자연어 요구사항
        |
AI 에이전트(Codex / Claude Code / 기타)
        |  게임 설계 · 아트 디렉션 · 제작/테스트 계획
        v
Futty MCP / CLI / 안정적인 JSON 계약
        |
공통 제작 서비스(기획 · 생성 · 편집 · 검증 · 빌드)
        |
+-------------------------+-------------------------------+
| Asset Generation Service| Game Authoring & Runtime      |
| 2D 이미지 생성 어댑터    | futty-core / futty-runtime    |
| 3D 모델/리깅 어댑터      | bevy_ecs / Rhai / Input / HUD |
| 애니메이션 생성 어댑터   | 장르 템플릿 / 씬 / 프리팹     |
| 효과음/BGM 생성 어댑터  | Fixed Tick / Script / Events  |
| 프로시저럴 fallback     |                               |
+------------+------------+-----------+-------------------+
             |                        |
       에셋 규격화/검증          2D / 3D 백엔드
       레지스트리/해시           Render2D / Render3D
             |                   Rapier2D / Rapier3D
             +--------------+---------+
                            |
                    futty-network (신규)
                 권한 서버 · 복제 · 보간
                            |
                 헤드리스 테스트/캡처
                            |
                    futty-build
                    /         \
                  Game.exe     Server.exe(향후)
                            |
                 실행 파일 / 에셋 / 리포트
~~~

**설계 규칙**
- 공통 ECS·씬·프로젝트 형식 유지. 2D·3D 표현·물리 백엔드는 별개로 두어 기존 3D 동작을 보존한다.
- **씬 차원**을 TwoD / ThreeD로 명시하고 구버전 씬에 필드가 없으면 ThreeD로 읽는다.
- 2D 좌표는 XY 평면, Y 위쪽, Z=0, 2D 회전은 단일 각도; 3D는 기존 Vec3·Quaternion을 유지한다.
- 서버가 공식 게임 상태를 결정한다. 전용 서버는 GPU/에디터가 없어도 실행되어야 한다.
- 생성형 AI 제공자와 클라이언트는 바꿔 끼울 수 있는 어댑터로 연결한다.
- 프로젝트/씬/에셋을 실제 사용하는 **공통 서비스**를 두고 MCP·CLI·GUI가 같은 검증 규칙을 사용하도록 한다.

### 크레이트 발전 방향(신규 이름은 설계안)

| 크레이트/모듈 | 책임 | 상태 |
| --- | --- | --- |
| futty-core / futty-runtime | ECS, 씬 포맷, 입력·스크립트, 고정 틱 | 기존 확장 |
| futty-render | 기존 wgpu 3D + 공통 렌더 서비스 | 기존 확장 |
| futty-render-2d | Sprite2D, TileMap, 카메라, 애니메이션, 배치 렌더 | 신규 |
| futty-physics-2d | Rapier2D 충돌·트리거·캐릭터 컨트롤러 | 신규 |
| futty-assets / futty-audio | PNG/GLB/WAV/OGG 검증·로딩·재가져오기 | 기존 확장 |
| futty-asset-pipeline | 이미지/3D/모션/음향 생성·규격화·프로비넌스 | 신규 |
| futty-network | 세션, 프로토콜, 복제, 예측·보간, 권한 검증 | 신규 |
| futty-server | 렌더러 없는 권한 서버 실행 진입점 | 신규 |
| futty-mcp | 안정적 AI 도구 계약, 편집/생성/검증 | 기존 확장 |
| futty-build | Windows 게임/전용 서버 및 종속 리소스 패키징 | 기존 확장 |
| futty-editor | 사람이 결과를 확인하고 선택적으로 편집 | 기존 유지·후순위 |

필요하다면 신규 기능은 처음에 기존 크레이트의 작은 모듈로 실험하고 안정화 후 분리한다.

## 4. 2D 게임을 실제로 완성하기 위한 기능

### 4.1 렌더링/씬

- [ ] Sprite2D: 알파 PNG, 레이어·정렬 순서, 배치 렌더링, 기준점/뒤집기, 색상 틴트.
- [ ] SpriteSheet/Atlas: 프레임 영역, 속도, 루프, 상태 기반 애니메이션 재생.
- [ ] TileSet/TileMap: 격자 배치, 반복 패턴, 충돌 타일, 타일 레이어, 대규모 맵 컬링.
- [ ] 2D 카메라: 정사영, 화면 비율, 추적, 줌, 픽셀 퍼펙트/픽셀 스냅 옵션.
- [ ] 2D 편집 및 MCP 읽기·쓰기·캡처, 2D/3D 씬 포맷 마이그레이션.

### 4.2 물리/게임플레이

- [ ] Rapier2D의 박스·원·캡슐 강체/콜라이더·센서·레이캐스트.
- [ ] 2D 중력·점프·탑다운 이동·충돌 레이어와 스크립트 이벤트.

## 5. 멀티플레이 — 2D와 3D에 공통 적용

### 5.1 네트워크 기본 구조

- **Authoritative Dedicated Server**: 서버가 이동/충돌/피해/점수/승리 등 공식 게임 상태를 계산한다.
- 초기 접속: 로컬호스트 → LAN → 직접 IP/호스트 온라인 접속. 글로벌 매치메이킹/자동 NAT 통과는 후순위.
- 서버가 게임 상태를 고정 틱으로 처리하고 클라이언트가 입력 시퀀스/시간을 전달한다.
- Connection/Session/Room/PlayerId, 입장·퇴장·타임아웃·재접속·프로토콜 버전을 정의한다.
- 신뢰성이 필요한 스폰/점수/승리 이벤트와 고빈도 위치 상태를 다른 전송 정책으로 취급한다.
- 네이티브 전송 계층 후보는 QUIC(예: quinn). 전송 라이브러리는 실제 구현 시 검증 후 선택한다.

### 5.2 시각 품질/복제

- NetworkIdentity, 소유권(서버/클라이언트), 복제 필드/관심 범위.
- 서버 상태 스냅샷·델타 전송, 클라이언트 보간, 로컬 입력 예측/재조정.
- 애니메이션은 서버 권한 상태/이벤트를 복제하고 **시각적 프레임 포즈는 로컬 재생**.
- 음악/효과음 원본 파일을 틱마다 전송하지 않고 관련 오디오 이벤트만 동기화.
- 패킷 손실/역순/중복, 잘못된 입력, 과속·순간이동, 권한 없는 조작을 테스트한다.

**초기 측정 가정(보장 수치 아님)**: 서버 시뮬레이션 60Hz, 스냅샷 10~20Hz, 2~4명 협동 예제로 시작. 네트워크 지연 100ms·손실/지터를 주입해 검증한다. 고정 틱으로 플랫폼 간 비트 단위 물리 결정성이 보장되는 것은 아니다.

**멀티 완료 조건**: Windows 서버 1개와 클라이언트 2개 이상이 실제로 접속해 동일한 플레이어/코인/승리 상태를 관찰하고, 중복 획득/부정 입력이 거절된다. 이어서 동일 네트워크 계층으로 3D 협동·FPS 테스트까지 통과한다.

## 6. 디자인·모델링·애니메이션·사운드까지 자동 제작

### 6.1 Art Direction이 모든 생성의 기준

요청을 받으면 AI가 **GameBrief + ArtDirectionSpec + AssetPlan**을 먼저 작성한다.

| 범주 | 반드시 정의할 내용 |
| --- | --- |
| 비주얼 콘셉트 | 장르·분위기·시대·형태 언어·색상 팔레트·광원 |
| 2D 아트 | 스프라이트 크기/피벗, 픽셀 밀도, 타일 규격, 프레임/레이어 |
| 3D 아트 | 스타일, Y-up, 미터/피벗, 폴리곤 예산, 텍스처·UV·머티리얼 |
| 캐릭터 움직임 | Idle/Walk/Run/Attack/Hit/Death, 루프·길이·전환·이벤트 |
| UI/UX | 로비/메뉴/HUD, 안전 영역, 대비·가독성, 버튼 상태 |
| 오디오 | SFX·환경음·BGM 역할, 음색, 음량/루프, 공간음 |
| 배포 권리 | 출처, 생성 제공자, 해시, 라이선스, 비용·허용 범위 |

캐릭터·맵·HUD·SFX가 서로 다른 스타일로 생성되지 않게 공통 스펙을 전달한다. 요청에 따라 새 모델을 만드는 것과 원본 에셋을 라이선스에 맞게 사용하는 것을 구분한다.

### 6.2 생성기 계약

1. **Prototype**: 오프라인 프로시저럴 이미지·기본 GLB·간단 WAV로 게임을 신속하게 실험. 결과물에 placeholder 표시.
2. **Assisted**: 실제 연결된 이미지·3D 모델·애니메이션·음향 생성 도구나 Blender 헤드리스 처리. 도구 이름·사용 권한·비용 기록.
3. **Production**: 아트 디렉션 준수, UV/리그/클립/루프/믹싱·재생 품질, 라이선스까지 검사한 뒤 final로 승격.

Futty는 생성형 모델을 직접 구현할 필요 없이 **모델 중립적인 어댑터**로 AI 이미지, 텍스트→3D, 리깅/모션, 음악/SFX 생성기를 호출할 수 있어야 한다. 생성 제공자가 없는 상황에서는 프로시저럴 대체가 가능하지만 최종 아트로 위장하지 않는다.

### 6.3 매체별 품질 게이트

- **2D**: 투명도·프레임 수·기준점·캔버스 크기·팔레트 일치·TileSet 경계·UI 대비.
- **3D**: 유효한 GLB, 기본 씬/삼각형 메시, 노멀/UV/텍스처, 스케일/방향/피벗, 적정 폴리곤, 불필요한 외부 참조 제거.
- **애니메이션**: 스켈레톤·관절·가중치, 클립 이름/인덱스, 루프/전환, 모델 재가져오기 시 참조 유지, 2D 시트 프레임 정렬.
- **오디오**: WAV/Ogg 재생 가능·길이·피크/클리핑·루프 이음새·배경음/효과음 밸런스·이벤트 바인딩.
- **실제 게임 연결**: 모델/사운드 파일이 존재하는 데 그치지 않고 게임 오브젝트·프리팹·Rhai·HUD에 연결돼 플레이로 검증되어야 한다.
- **출처/보안**: 콘텐츠별 생성 모델/도구, 해시, 재생성 버전, 라이선스/동의, 유료 API 사용 권한.

**현재 첫 발판**: [프로토타입 생성기](../scripts/generate-prototype-assets.py)는 한 명령으로 원본 PNG 4개·Idle/Action 애니메이션 GLB 1개·WAV 3개·아트 디렉션 JSON·해시 매니페스트를 만드는 **코드를 보유**한다. [기본 형식 검증 테스트 소스](../scripts/test_prototype_asset_pack.py)도 있다. 이것은 외부 생성형 AI가 만든 고급 캐릭터/전문 BGM이나 Futty 씬 자동 적용을 의미하지 않는다.

### 6.4 에셋 상태 전이(목표)

~~~text
Planned → Generated → Validated → Imported → Bound → Tested → Final
              |           |            |
            Failed      Rejected      Rework
               \___________|____________/
                       Retrying
~~~

검증 실패를 숨기지 않는다. 에셋은 안정적인 UUID/해시/출처를 갖고, 재생성·재가져오기 시 참조를 보존한다. 다량 생성 작업에는 Job ID·상태 조회·취소·비용 상한·재시도 횟수 제한이 필요하다.

## 7. AI 제작 도구의 계약

### 공통 API 원칙

1. 외부 MCP/CLI가 재사용 가능한 **공통 제작 서비스**를 호출한다. GUI 안에서만 가능한 핵심 작업을 만들지 않는다.
2. 모든 입력/출력에 명시적인 JSON 스키마와 버전, 단위/좌표계, UUID, 필수값/기본값/제약값을 둔다.
3. **읽기/쓰기 대칭**: AI가 변경한 상태를 다시 조회·검증할 수 있다.
4. 여러 수정은 사전 검증하고 원자적으로 적용하며, 충돌·실패 시 변경 내역과 되돌리기 방안을 제공한다.
5. 재시도 시 자산/오브젝트 중복 생성 방지(idempotency), 작업 버전·에셋 해시·편집 충돌 감지.
6. 실패는 오류 코드·필드 경로·씬/오브젝트 ID·서버 틱·로그/스크린샷 경로로 구조화한다.
7. 긴 생성·테스트 작업은 Job ID, 상태 조회, 취소, 리포트가 가능해야 한다.
8. 생성 제공자 비용/사용 제한과 파일 경로/작업 영역 제한을 검증한다.

### 앞으로 필요한 고수준 API(전부 **설계안**, 실제 구현이라고 가정 금지)

| 영역 | 예시 API | 목표 |
| --- | --- | --- |
| 장르·프로젝트 생성 | game_create_from_template, scene_generate_layout | FPS/플랫폼/퍼즐 시작 프로젝트 및 시드 맵 |
| 일괄 편집·차이 | scene_preview_ops, scene_diff | 적용 전 변경 내역/참조 영향 |
| 2D | scene_set_dimension, sprite2d_create, tilemap_apply, physics2d_set_body | 완전한 2D 제작·검증 |
| 에셋 제작 | game_brief_create, art_direction_set, asset_plan_create, asset_generate | 자연어→통일된 스타일 에셋 |
| 에셋 연결 | asset_import_batch, asset_bind, animation_bind, audio_cue_bind | 생성 파일을 게임에 연결 |
| 멀티 설정 | network_configure, network_set_replication, network_set_authority | 서버/룸/복제 권한 |

유사 기능은 무조건 새 MCP 도구를 늘리기보다 기존 scene_apply, project_validate, play_test 등과 **스키마를 공유**하도록 설계한다.

## 9. 자동 검증·성공 지표

### 모든 기능에 적용할 테스트 매트릭스

### 추적할 지표

- 필수 사람 GUI 조작 횟수 **0회**.
- MCP/CLI로 호출 가능한 핵심 제작 기능 비율.
- 단일 프롬프트 기준 자동 완주율과 재시도 성공률.
- 빌드·검사·플레이테스트 실패 원인을 구조화해 수정할 수 있는 비율.
- 새 폴더에서 재현 가능한 E2E 성공률.
- 모델/에셋 생성 시간·비용, 게임 성능, 네트워크 지연/패킷 손실에서의 안정성.
- 완료한 게임의 에셋 출처/라이선스/placeholder 잔존 수.

## 10. 품질·보안·재현성·라이선스 원칙

- **기존 게임 호환성**: 저장 형식 버전 관리, 하위호환 마이그레이션, UUID/에셋 참조 보존.
- **워크스페이스 격리**: 경로 탐색 차단, 원자적 파일 저장, 파일 크기/형식 검증, 작업 충돌 방지.
- **네트워크 신뢰 경계**: 클라이언트 입력 권한·주기·크기를 서버 검증; 공격/아이템/점수는 서버 판정.
- **AI 제공자 비용**: 실제 연동된 서비스만 이용하고 비밀키를 GitHub/프롬프트 로그/게임 번들에 기록하지 않는다. 유료 사용은 사용자 승인·예산 한도를 따른다.
- **저작권/제3자 리소스**: 이미지·모델·음원·음성 출처, 사용 권한, 재배포 조건과 생성 이력을 보존한다.
- **정직한 품질 선언**: 프로시저럴 모델/합성음은 prototype. 이용자에게 production 품질이 보장된 것처럼 표시하지 않는다.
- **재현성**: 생성 시드·모델/도구 버전·파일 해시·스크립트·테스트 틱 기록; 외부 생성형 모델은 출력이 완전히 결정적이지 않을 수 있으므로 산출물 버전을 보존한다.
- **비목표**: 모든 엔진 기능을 자체 개발해야 한다는 원칙, 특정 모델 종속, 첫 버전부터 대규모 MMO나 모든 플랫폼 지원.

## 11. 최종 수락 테스트: 한 번의 요청으로 완성 게임

아래 세 데모가 **서로 다른 새 폴더에서 반복 성공**해야 전체 제품 목표를 달성한 것으로 판정한다.

1. **3D 단일 게임**: 새 프로젝트에서 3D 코인 수집 또는 FPS 연습장을 만들어 입력·HUD·충돌·승리 조건을 검증하고 Game.exe를 생성.
2. **2D 멀티 게임**: 4인 Co-op Coin Hunt를 만들고 서버 1개/클라이언트 2개 이상의 접속·이동·수집·중복 방지·종료 판정을 테스트한 뒤 Game.exe/Server.exe 생성.
3. **3D 원스톱 멀티**: 공통 아트 디렉션에 맞는 맵·모델·텍스처·리그/동작·HUD·효과음·BGM을 만들고 실제 게임 이벤트에 연결한 3D 협동 게임을 검증·패키징.

**최종 합격 조건**
- 에디터 GUI 필수 조작이 없다.
- 모든 필수 에셋이 placeholder가 아닌 **요청 품질에 부합한 결과물**이거나, 남은 placeholder를 명시적으로 미완료 처리한다.
- 구조·플레이·애니메이션·사운드·네트워크·빌드 검증 기록이 있다.
- 실행 가능한 결과물과 라이선스/출처가 포함된다.
- 오류가 남아 있으면 완성이라고 말하지 않고 재현 가능한 실패 리포트를 제공한다.
